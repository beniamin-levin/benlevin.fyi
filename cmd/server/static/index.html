An autonomous AI agent that validates GitHub bug reports

Python 3.12 · asyncio · FastAPI · Pydantic · Docker · MCP server · NVIDIA Nemotron

A bug report shouldn’t be marked fixed because an LLM thinks the patch looks right. FixedYet writes a reproduction test, runs it in a sandbox at the reported version and on current main, and lets deterministic rules, not the model, decide the verdict. It can then test a proposed fix or backport in the sandbox and open a draft pull request. I built it solo, to answer the two questions a maintainer actually has: is the bug real at the reporter’s version, and is it already fixed?

How it works

GitHub issue → Nemotron writes a pytest reproduction → sandbox runs it at the reported version and on main → deterministic verdict → fix or backport, proven in the sandbox → draft PR

NVIDIA Nemotron on Nebius Token Factory writes the pytest reproductions, Docker isolates each run, and deterministic rules, not the model, decide the verdict: fixed, open, or not reproduced. For a bug that is still open it writes a fix; for one already fixed on main it verifies the backport to the reporter’s release line. A change counts only when the reproduction fails before it, passes after it, and the project’s own suite shows no new failure.

Results
  • 11–13 of 15 issues of a SWE-bench Verified subset reproduced per run, at ~$0.03 of model cost each (a small subset, not comparable to the public leaderboards)
  • 8 of 10 correct verdicts on recent live GitHub issues, a separate set run as a check against training-data overlap; the other 2 were flagged at low confidence
  • Four upstream PRs that its fixes and backports led to, including Black (42k stars), Pydantic, and RDFLib (merged); I finished them after maintainer review
  • 1,700+ pytest tests in the project itself
What building it taught me

Passing tests isn’t the same as correct. FixedYet’s first RDFLib fix passed the whole suite but also changed SPARQL MIN and MAX; review caught it, and the merged fix took a different approach. Scope, plainly: pure-Python projects tested with pytest.

Production wind-monitoring app for kitesurfers on the Israeli coast

Go · MySQL · Oracle Cloud (OCI) · systemd · Docker · Telegram

Kitesurfers on the Israeli coast decide whether to drive an hour based on wind that changes in twenty minutes. Public sources are scattered, slow, and mostly Hebrew PDFs. I built the thing I wanted to exist, then kept it running.

Architecture

Windguru + Israeli stations → Go collectors every minute (systemd timers) → MySQL → Go web app → charts, beach cameras, Telegram and browser alerts

Live station readings, historical charts, beach cameras, and wind and storm alerts, on Oracle Cloud. Go collectors ingest Windguru and Israeli station data into MySQL every minute and send wind and storm alerts through Telegram and browser notifications. They run on independent systemd timers, so one flaky upstream cannot stall the others; development runs on a Docker-based setup.

Why I rewrote it from PHP to Go

The 2023 PHP version worked, but every collector was a separate cron-invoked process paying full interpreter startup, and concurrent polling meant either blocking or process sprawl. Go gave me goroutine-per-collector concurrency, a single static binary to deploy, and a memory profile that fits comfortably inside a free-tier VM. The 2026 rewrite is the version running today.

What running it taught me

Upstream feeds fail in undignified ways — a station returns yesterday’s reading with today’s timestamp, a PDF layout shifts, a file arrives truncated. Most of the engineering is not the happy path; it is staleness detection, per-source backoff, and alerting that distinguishes “no wind” from “no data”.
